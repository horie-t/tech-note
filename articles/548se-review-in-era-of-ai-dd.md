## レビュー疲れはなぜ起きるのか

世の中の御多分に漏れず、私もAI駆動開発をやっています。そして、コードを自分で書くこともなくなりました。AI駆動開発でのコード生成の速さに驚きつつ、今までの苦労は何だったのかと、少し虚しさを感じています。

ですが、これで苦労はなくなった、めでたしめでたし、というわけではありません。AI駆動開発では、コードの生成は速くなりましたが、レビューの必要性は変わりません。あっという間に生成されたコードのレビューと、同僚からの大量の「実装しました。レビューをお願いします。」の一言とともに、レビューの嵐に巻き込まれています。

何故こうなったのかを考えてみましょう。今までの自身のコーディングと同僚のコードレビューの時間の使い方を振り返ってみます。例えば、同僚がコードを書く時間の10分の1の時間でレビューをしていたと仮定します。そして、自身の担当のコードを書く時間の割合がスクラム開発のスプリントの中で30%だったとします。自分で書いたコードの自己レビューは書きながら済ませていたので、コードを書く時間に対して誤差の範囲しか掛かっていなかったとします。同僚のコードのレビューに掛ける時間は15%だったとします。つまり、コーディングとレビューで使っていたのは合わせて45%で、残りの55%は設計や会議などに使っていたことになります。

さて、AI駆動開発です。自分で書いたコードと違い、AIが生成したコードは中身を把握していません。ですから、同僚の書いたコードと同じように、書く時間の10分の1の時間を掛けてレビューする必要があります。そして、コードの生成に掛ける時間は今までと同じ30%のままで、生成されるコード量が10倍になったとします。この時、レビューの時間はどれだけ必要になるでしょうか。まず、自身の生成したコードは人が書けば300%の時間が掛かる量になるので、そのレビューに30%の時間が必要になります。さらに、同僚のコードの生成量も10倍になるので、同僚のコードのレビューに掛ける時間も10倍の150%になります。この時間を合計すると、コード生成の30% + 自身のコードのレビューの30% + 同僚のコードのレビューの150% = **210%**になります。今まで45%で収まっていたものが210%、およそ4.7倍です。レビューだけでもスプリント期間の1.8倍、これに設計や会議の55%を足せば265%です。破綻していますね。

表にまとめると、こうなります。

| 項目 | AI駆動開発前 | AI駆動開発後 |
| --- | --: | --: |
| コードの生成 | 30% | 30% |
| 自身のコードのレビュー | 誤差の範囲 | 30% |
| 同僚のコードのレビュー | 15% | 150% |
| コーディングとレビューの小計 | 45% | 210% |
| 設計や会議など | 55% | 55% |
| **合計** | **100%** | **265%** |

では逆に、スプリントに収まる範囲でどれだけのコード量を扱えるのでしょうか。今までコーディングとレビューに使っていた45%に収める条件を考えてみます。扱うコード量を今までの k 倍とすると、必要な時間はそれぞれこうなります。

- コードの生成: 10倍の量を30%で生成できるので、k 倍なら 3k%
- 自身のコードのレビュー: 10倍の量で30%なので、k 倍なら 3k%
- 同僚のコードのレビュー: 10倍の量で150%なので、k 倍なら 15k%

合計は 21k% です。これが45%に収まる条件は k ≒ **2.1**。生成が10倍速くなっても、レビューしきれるコード量は今までの2倍強でしかありません。

しかも、これはコード生成が速くなればなるほど良くなる話ではありません。生成に掛かる 3k% が仮に0になったとしても、レビューの 18k% は残ります。45 ÷ 18 = **2.5倍**が天井です。

| コード生成の速さ | レビューしきれるコード量 |
| --: | --: |
| 2倍 | 1.4倍 |
| 10倍 | 2.1倍 |
| 100倍 | 2.5倍 |
| いくら速くても | 2.5倍 |

コード生成が速くなったこと自体から得られる開発量の伸びは、高々2.5倍です。(ここでは議論しませんが、増えたコードを書くためには要件定義や設計のミーティングや工数も増えますので、もっと少ないでしょう。) それ以上を望むなら、まずはレビューのやり方そのものを変えるしかありません。

## 人間同士のピアレビューの意義

レビューをどう変えるかを考える前に、そもそも今まで人間同士のピアレビューが何をしてきたのかを整理しておきます。一口にレビューと言っていますが、そこには目的の異なる複数の営みが同居しています。

### 1. 欠陥を見つける

まず思い浮かぶのはこれでしょう。仕様や要求と一致しているか、つまりそもそも作るべきものを作っているかを確かめます。ロジックの誤り、境界値や異常系の抜け、エラー処理と失敗したときの状態の扱いを追います。並行処理での競合状態やリソースの解放漏れのような、動かしただけでは再現しにくい問題も見ます。セキュリティも同じで、入力の検証、認証・認可、機密情報の取り扱い、追加された依存ライブラリの素性を確認します。性能やスケーラビリティ上の懸念もここに含まれます。そして、テストが変更内容を実際に守っているか、抜けている観点がないかを見ます。

### 2. 設計と保守性を守る

そのコードが動くかどうかとは別に、そのコードと数年付き合えるかを見ます。既存のアーキテクチャや設計方針と整合しているか、責務が適切に分かれているか、重複が生まれていないか。命名と可読性、コーディング規約への準拠。不要な複雑さや、使われるかも分からない汎用化を持ち込んでいないか。依存関係の追加や技術選定が妥当か。コメントやドキュメントが整っているか、負債を承知で通すのであればそれが明示されているか。ここでの指摘は動作を何も変えませんが、将来のコストは大きく変えます。

### 3. 変更を安全に届ける

コードの中身だけでなく、それをリリースするという行為のリスクも見ます。差分の範囲が適切か、無関係な変更が混入して巨大になっていないか。後方互換性、データ移行、設定値やフィーチャーフラグの扱いはどうか。ログやメトリクスなど、運用で必要になる手当てがされているか。問題が起きたときに切り戻せるか。コミットメッセージやプルリクエストの説明が、半年後に読んで意図を辿れるものになっているか。レビューはリリースの前に立つ最後の関門でもあります。

### 4. チームに知識を残す

ここからはコードそのものではなく、チームに対する効果です。レビューを通すと、そのコードを知っている人が最低でも2人になります。属人化が防げて、バス係数が上がります。設計思想や規約は、文書で配るよりも実際のコードへの指摘を通じたほうがよく伝わります。新しいメンバーの育成は、ほとんどこれで進みます。さらに、レビューを経ることでコードが「誰かのもの」ではなくチームのものになり、他人が書いた箇所にも手を入れられるようになります。レビューの記録は、変更が第三者に確認された証跡でもあり、監査や規制対応の場面で効いてきます。
