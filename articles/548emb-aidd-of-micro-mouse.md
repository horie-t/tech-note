以前の記事で[AI駆動開発でCRUDだけのSaaSアプリを作ってAWSにデプロイ](https://zenn.dev/thorie/articles/548se-ai-driven-development)してみたら、割とあっさりと出来上がってしまいました。これで、もう自分は仕事でのコーディングをすることないと思いしらされました。

でも分野を変えればまだ人間の手が必要なこともあるのではないかと思い、組み込み開発っぽいことをやってみようと思い立ちました。そこで[マイクロマウス](https://www.ntf.or.jp/?page_id=25)を作ることにしました。最近はFableやGPT 6 Astraで電子回路やCADデータを生成できると話題になっていますが、作ろう思い立ったのが6月の末で、その頃はまだ回路設計や機械設計の話題がない時期だったので自分で設計することにし、ソフトウェアの部分だけをAI(Claude Code)に任せることにしました。

マイクロマウスは古くから存在するのでマイクロマウス用のソースコードをAIが学習してその学習データを出力しているだけって結論になるのは避けたいと思い、あまりマイクロマウスで使われていないハードウェアの構成で製作しました。

最初に以下のようなプロンプトを打って、開発の計画を立ててもらいました。

```
❯ マイクロマウスの大会に出るためのアプリケーションを作成します。計画を立てるの
  を手伝ってください。

  ハードウェアは以下の通りです。
  - Raspberry Pi 5
  - オムニホイール (直径: 48 mm, 幅: 25.5 mm) 3個
  - ステッピングモーター (ステップ角: 1.8°) 3個
  - モータードライバー L6470 3個
  - センサー（9軸センサー）: BNO055
  - カメラ (壁近接検知見下ろしカメラ): Raspberry Pi カメラモジュール V3（広角）

  カメラは下向きに取り付けて、壁の上部の赤い部分が見えるような状態にします。
```

不明な点についての質問に以下のように回答しました。

```
· 主要なプログラミング言語/フレームワークはどれにしますか？ → Python (推奨)
· 最初に作る成果物（マイルストーン1）はどれにしますか？ → 
  ハードウェア基盤から (推奨)
· 対象とする迷路は標準のクラシック・マイクロマウス迷路ですか？ → 
  標準16×16クラシック
```

計画を立ててPlanのmdファイルを作成しようとするのですが、進捗管理はGitHubの[マイルストーン](https://github.com/horie-t/krilly/milestones?state=closed)と[issue](https://github.com/horie-t/krilly/issues?q=is%3Aissue%20state%3Aclosed)で管理することにしました。

回路関係はAIによる補助はなしで進めるつもりだったのですが、はんだ付けをミスって回路をショートさせてしまいモーターが動かない状態になってしまって、AIに以下のように泣きついてしまいました。

```
L6470の駆動ですが、一部のドライバ基盤が壊れているようで、まずはディジーチェーンではなく、1つづつ動作確認をしたいです。    
```

AIは破損個所の切り分け方法を考えてくれて、AIに言われるがままに配線を組み替えていき「組み替えました」とAIに伝えると、AIがRaspberry PiのGPIOのピンを操作するスクリプトを書いてくれて、壊れているピンまで特定して代替のピンを使うように提案してくれました。もはやAIが設計者で、私はAIの指示に従うだけの作業者になってしまったと感じた瞬間でした。

更に横着になってくると、スクリプトの実行すら以下のように依頼していました。

```
❯ あなたは今Raspberry Pi上で動いています。 1. を実行してみてください。
```

ただし、完全にお任せ状態にはできず、ちょくちょく間違った判断をするので以下のような感じで、疑問を投げかけて確認させる必要があります。

```
❯ 「Pi の I2C はクロックストレッチが苦手」はRaspberry Pi 5でも該当しますか?     
```

このように、勘違いを指摘すると以下のように訂正してきますので、AIの判断が本当に正しいのかどうかを見定めるスキルは必要でした。

```
● 良い質問です。結論: あの有名なクロックストレッチ問題は Pi 5には基本的に該当しません。
  先の私の案内（研究時の「Pi 5でも該当」）は不正確でした。訂正します。
```

コードのレビューをどうするのかが現時点でのAI駆動開発での共通の課題になっていますが、作業時間の大半がレビューになってしまっている事に気付いてからはレビューはせずに実機での動作確認のみをするだけになりました。この点は本当に良かったのだろうかと、未だ思案中です。


ハードウェアの制御では位置の測定や制御の誤差が生じるのでその値を実験して測定する必要があるのですが、実験の計画や測定値の集計やバラつきの評価までAIが行う流れになってしまい、ここでも私がAIの手足となって実験するだけの作業者でした。
