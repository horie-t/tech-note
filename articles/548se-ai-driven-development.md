普段の業務でもAIを使って開発するようになり、ここ3ヶ月ほどは自分ではコードを書かずにアプリケーションを作れるようになってきています。しかし、ブラウンフィールド開発という事もあり細かく指示をしないとAIが思った通りに動かないことも多く、そんなに開発速度が上がっている実感はありませんでした。では、スクラッチからの開発であればどうだろうかと、週末の2日間でAI駆動開発を使って家計簿SaaSを作ってみて、これからの開発のあり方を考えてみました。

# AI駆動開発で家計簿SaaSを作ってみた

作ってみたのは、以下のような画面を持つ家計簿SaaSです。ソースコードは[GitHub](https://github.com/horie-t/sumika)に公開しています。

![家計簿SaaSのメイン画面](/images/aidd-house-keeping-main.png)

![家計簿のレポート画面](/images/aidd-house-keeping-report.png)

## 技術スタック

使用した技術スタックは以下の通りです。

- コーディングエージェント: Claude Code
- フロントエンド: React + TypeScript
- フロントエンドテスト: Vitest + React Testing Library + playwright-bdd
- バックエンド: Spring Boot + Java
- バックエンドテスト: JUnit + REST Assured + PICT
- データベース: AWS Aurora PostgreSQL Serverless
- IaC: Terraform
- CI/CD: GitHub Actions
- デプロイ: AWS ECS Fargate + CloudFront + S3
- プロジェクト管理: GitHub Projects

aidlc-workflowsのようなAI駆動開発のツールは使用しませんでした。

## 開発の進め方

開発は以下の流れの繰り返しで進めました。

1. Claude CodeのPlanモードで、ある程度までの実装したい部分について相談しながら計画を立てる
2. 計画が決まったら、GitHubでMilestoneを作成し、Issueを作成させる
3. Issueの内容をもとに、Claude Codeのautoモードでコードを生成させ、PRを作成させる
4. PRの内容を自分でレビューし、必要に応じて修正を指示する
5. PRをマージさせ、CI/CDでデプロイする

## 実際の開発の様子

### アプリケーション名の決定
まずはアプリケーション名を決めるところから始めました。筆者はネーミングセンスがないので、ClaudeのDesktop版で以下のように相談して、いくつかの候補を出してもらいました。

> 家計簿の管理アプリの名前の候補を5つ挙げてください。各候補はできるだけ違った由来の名前にしてください。

```text
1. **カケトル** — 「家計」を「捕(と)る・記録する」イメージの和製造語。
2. **Obolus（オボルス）** — 古代ギリシャの小額硬貨の名前から。お金そのものを象徴する古語由来。
3. **やりくり帳** — 限られたお金を上手に回す「やりくり」という日常語からの素直なネーミング。
4. **Penny Lens（ペニーレンズ）** — 「ペニー（小銭）」を「レンズで観察する=支出を見える化する」という英語の比喩から。
5. **Sumika（スミカ）** — 計算の「Sum(合計)」と、暮らしの場所「住処(すみか)」を掛け合わせた造語。
```

本当にサービスとして運用するつもりはなかったので、ダジャレっぽい名前の「Sumika」に決定しました。

### レビューについて

生成されるコードは優秀なエンジニアが書いたコードという感じでしたが、作業内容自体は漏れや確認不足のおおいおっちょこちょいなエンジニアという印象でした。

最初にアーキテクチャを決めているので、それに沿ったコードが生成され、ネーミングも悪くありませんでした。レビューはコードを1行ずつ見ていくというよりは、コードを眺めて作業に漏れがないかを確認するという感じでした。この辺は、細かいところまでチェックをするエンジニアリング・マネージャーのような感じでした。また、実際に動かしてみて動作確認をするということも必要なので、QAとしての役割も担っている感じでした。

とにかく実装速度が速いので、レビューがボトルネックにならないように、レビューのやり方を工夫する必要がありました。例えば、PRの内容をまとめてくれるので、まずはまとめを読んで、問題なさそうであれば「マージして次に進めて」と指示するという感じでした。

### Four keysのメトリクスの観点でのパフォーマンスをエリートにする

ローカルPC上でMVPが動くようになったので、プロダクトオーナーがユーザーとして使えるように、AWS ECS Fargateにデプロイしてみました。[Four keysのメトリクス](https://cloud.google.com/blog/ja/products/gcp/using-the-four-keys-to-measure-your-devops-performance)の観点で、開発速度をエリートにするために、デプロイの自動化を進めました。

もう一度、Planモードで以下のように相談して、[デプロイの自動化の計画](https://github.com/horie-t/sumika/milestone/6)を立てました。

> 次にAWSへデプロイするCDパイプラインの構築を計画します。まだPoC段階なので可用性についての考慮は不要です。バックエンドはECSのFargate Spotで構築しようと考えています。フロントエンドはどのようにデプロイするのが良いか案を挙げてください。

MVPの計画の時と同様にClaude Codeが質問してくるので、回答して計画を立てていき、決定したら実装に進めました。

### テストの充実

AI駆動開発ではローカルでのテストを通るだけのコードが生成される問題が指摘されています。そのため、E2Eテストを充実させることで、ローカルでのテストが通るだけではなく、実際に動作するコードを生成させるようにしました。以下のように、Planモードで相談して[テストの充実の計画](https://github.com/horie-t/sumika/milestone/7)を立てました。

> バックエンドのAPI自動テストの構築の計画をします。                             
> Java言語を使ったAPIテストツールで良く使われているフレームワークやライブラリを3つ挙げてください。

ただし、E2Eテストの充実は、テストの実行に時間がかかるので、開発速度を上げるという観点では逆効果になる可能性があります。そこで、Planモードで以下のように相談して、テスト項目数を絞るようにしました。

> テストコードのレビューはJava言語で開発しているエンジニアが行うのでREST Assuredで進めたいです。                                                       
> ただし、進める前にE2Eテストですので、テストの網羅性は高く、しかしテストの項目 数は少なくしたいです。ペアワイズ法を使うようにしたいと思いますが、ペアワイズ法のツール等と組み合わせのしやすさ、保守のしやすさについて教えてください。

フロントエンドについては、プロダクト・オーナーもテスト内容を確認できるように、自然言語でテストする方法について相談しました。

> 続いては、Playwrightを使ったブラウザからのE2Eテストの構築をしたいと思います。 
> テストコードは、プロダクト・オーナーも読みやすいような自然言語をベース(日本語、もしくは簡単な英語に日本語混じりで書けるもの)にしたものが望ましいのですが、良いフレームワーク等はありますか?
> なければ、Gherkinファイルでテスト仕様を書いて、実装は別のプログラミング言語(できればフロントエンドと同じTypeScript)でも良いです。

### 機能の充実

ここまでで、AI駆動開発を進めていく上でのハーネスが整ったので、一気に機能を充実させることにしました。[レポート機能](https://github.com/horie-t/sumika/milestone/4)や[認証機能](https://github.com/horie-t/sumika/milestone/5)、[UIのモダナイゼーション](https://github.com/horie-t/sumika/milestone/9)を行いました。

認証機能の追加のようなDBのスキーマ変更を伴うような大きな変更は、ローカルPCでのテストは成功してもデプロイ時にエラーが発生したので、ステージング環境での確認の重要性を実感しました。

## AI駆動開発でグリーンフィールド開発を進めてみての感想と開発のあり方の考察

たった2日間でCRUDとレポート機能を持ったSaaSアプリケーションの開発を、ローカルPC上でのMVPからデプロイまでを行うことができました。ここまでの速度で開発できるなら、新規の案件では打ち合わせの資料を充実させるよりも、まずはMVPを作ってみて、ユーザーに触ってもらいながら改善や追加項目を洗い出して契約を進めるというやり方が良いのではないかと思いました。

また、AI駆動開発を進めていく上で、Planモードでの計画の立案や、テストの充実、デプロイの自動化など、開発速度を上げるためのハーネスを整えることが重要だと感じました。これらのハーネスが整っていないと、AI駆動開発のメリットを最大限に活かすことができません。レビューやQAの部分は、AI駆動開発ではまだまだ人間のエンジニアが必要だと感じました。AIが生成するコードは優秀ですが、漏れや確認不足があるため、レビューやQAの役割は重要です。コーディング・スタイルを統一するためにLinterを使うというような事は些末な事に見えました。

コードを書くという作業を手放したエンジニアは、これからは開発計画や進捗管理のプランナー、AIの作業の承認者、QAの部分に注力することになるのでしょうね。
