以前の記事で[AI駆動開発でCRUDだけのSaaSアプリを作ってAWSにデプロイ](https://zenn.dev/thorie/articles/548se-ai-driven-development)してみたら、割とあっさりと出来上がってしまいました。この結果を見て、もう自分は仕事でのコーディングをすることないだろうと思いしらされました。

ですが、分野を変えれば、まだ人間の手によるプログラミングが必要なこともあるのではないかと思い、その分野を求めて組み込み開発っぽいことをやってみようと思い立ちました。試しに[マイクロマウス](https://www.ntf.or.jp/?page_id=25)を作ることにし、その結果と感想をまとめてみました。

## 制作の方針とその結果

最近はFableやGPT 6 Astraで電子回路や機械のCADデータを生成できると話題になっています。ですが、作ろう思い立ったのが6月の末で、その頃はまだ回路設計や機械設計の話題がない時期だったので自分で設計することにし、ソフトウェアは基本的にAI(Claude Code)に任せてAIが詰まったら人手で修正し、回路(といってもモジュール基板を接続するだけですが)と筐体は人手で設計することにしました。

この方針で進めたところ、ソフトウェアについては人手でのコーディングは一切なく、方針をAIに伝えてAIがおかしな判断をしていないか、実装したものが意図通りに動作するかを確認するだけでした。

また回路については、最初は自分で手作業でやっていたのですが、老眼のためはんだが良く見えない状態で作業していたら、はんだ付けをミスって回路をショートさせてしまいました。それが嫌でブレッドボードを使っていたら、大会の会場に持っていったらケーブルの接続不良が発生してしまいました。これは辛いということで、AIにモジュール間を接続する中継基板のCADデータと注文部品リストを作ってもらって、基板を発注して組み立てることになりました。

また、筐体についても大会の会場に持っていったら、筐体のネジが緩んでしまい、姿勢制御や迷路の探索に使うカメラの位置がずれてしまい、迷路の探索がうまくいかなくなってしまいました。この辺の問題の解決もAIに質問しながら対策を打っていくという形になりました。

一度目は大会の会場でリタイアしてしまいましたが、二度目は無事に[完走して特別賞](https://sites.google.com/a/itolab-ktc.com/mouse_hokuriku/%E7%AC%AC13%E5%9B%9E%E3%83%9E%E3%82%A4%E3%82%AF%E3%83%AD%E3%83%9E%E3%82%A6%E3%82%B9%E9%87%91%E6%B2%A2%E8%8D%89%E3%81%AE%E6%A0%B9%E5%A4%A7%E4%BC%9A)(マイクロマウスクラシック競技でkrillyというロボット名で出場しています)を頂きました。

## 製作したマイクロマウスの紹介

どのようなマイクロマウスが出来上がったかは、AIに作ってもらった[Krilly — 3輪オムニのマイクロマウス](https://claude.ai/artifact/9PHH9Xcu4nVGaPnvLEpGiN#slide-3dd33bdac6c2)と[最速ランの「止まる・測る・直す」](https://claude.ai/artifact/CLBPUNr2zpx3i77Avu3sWB#slide-3dd33bdac6c2)の資料を見てもらう事として、ここでは詳細は述べません。コードのリポジトリは[GitHubのkrilly](https://github.com/horie-t/krilly)にあります。

## 製作の過程

### プロジェクトの計画

マイクロマウスは古くから存在するので、公開されているマイクロマウス用のソースコードをAIが学習してその学習データを出力しているだけって結果になるのは避けたいと思い、あまりマイクロマウスで使われていないハードウェアの構成で製作しました。

最初に以下のようなプロンプトを打って、開発の計画を立ててもらいました。

```
❯ マイクロマウスの大会に出るためのアプリケーションを作成します。計画を立てるの
  を手伝ってください。

  ハードウェアは以下の通りです。
  - Raspberry Pi 5
  - オムニホイール (直径: 48 mm, 幅: 25.5 mm) 3個
  - ステッピングモーター (ステップ角: 1.8°) 3個
  - モータードライバー L6470 3個
  - センサー（9軸センサー）: BNO055
  - カメラ (壁近接検知見下ろしカメラ): Raspberry Pi カメラモジュール V3（広角）

  カメラは下向きに取り付けて、壁の上部の赤い部分が見えるような状態にします。
```

不明な点についての質問に以下のように回答しました。

```
· 主要なプログラミング言語/フレームワークはどれにしますか？ → Python (推奨)
· 最初に作る成果物（マイルストーン1）はどれにしますか？ → 
  ハードウェア基盤から (推奨)
· 対象とする迷路は標準のクラシック・マイクロマウス迷路ですか？ → 
  標準16×16クラシック
```

計画を立ててPlanのmdファイルを作成しようとするのですが、進捗管理はGitHubの[マイルストーン](https://github.com/horie-t/krilly/milestones?state=closed)と[issue](https://github.com/horie-t/krilly/issues?q=is%3Aissue%20state%3Aclosed)で管理することにしました。

### 電子回路の設計と製作

ユニバーサル基板でのはんだ付けをミスって回路をショートさせてしまいモーターが動かない状態になってしまって、AIに以下のように泣きついてしまいました。

```
L6470の駆動ですが、一部のドライバ基盤が壊れているようで、まずはディジーチェーンではなく、1つづつ動作確認をしたいです。    
```

AIは破損個所の切り分け方法を考えてくれて、AIに言われるがままに配線を組み替えていき「組み替えました」とAIに伝えると、AIがRaspberry PiのGPIOのピンを操作するスクリプトを書いてくれて、壊れているピンまで特定して代替のピンを使うように提案してくれました。もはやAIが設計者で、私はAIの指示に従うだけの作業者になってしまったと感じた瞬間でした。

更に横着になってくると、スクリプトの実行すら以下のように依頼していました。

```
❯ あなたは今Raspberry Pi上で動いています。 1. を実行してみてください。
```

ユニバーサル基板でのすずメッキ線のはんだ付けは老眼には辛いという事で、ブレッドボードをジャンパー線で接続して動作確認をしていたのですが、ブレッドボードは接触不良が起きやすく、大会の会場に持っていったら接触不良が発生してしまいました。その結果、以下のようにAIに依頼する事になりました。

```
> 回路回りでのトラブルが試走会以前の開発を含め、何度か発生しています。システム構成は決まったのでPCBを作りたいです。
```

作成されたCADデータを見ると部品の配置が変に偏っていたり、シルク印刷の文字が部品の下に来たりと、画像の認識や空間把握が苦手なようで、人手で位置調整したりしましたが、論理的部分は問題ありませんでした。ソフトウェアの世界での2025年半ば頃の状態に近いと感じました。

### 機体の設計と製作

筐体の設計は人手で行いましたが、3Dプリンタで設計した部品についてはAIに任せても可能だったような気がしています。振り返ってみると、AIに任せてみても良かったなと思います。

それから、私は機械設計については全くの素人なので、大会会場への輸送のような事は全く考慮できておらず、ネジが緩んでいたり筐体がねじれていたりで、校正をやり直す必要がありました。その辺を愚痴っていたら大会会場で他の参加者に「ロックタイトやダブルナットを使ったら？」とアドバイスをもらい、戻ってからAIに以下のように相談して対策を打つことになりました。

```
> 試走会で天板のネジが緩んでいました。原因は車のトランクにおいて輸送(距離: 700km)した影響だと思います。緩み止めナットを使おうと思いますが、一般的な緩み止めナットの仕組みについて教えてください。
```

```
> 他にロッドを4本使っていますが、ねじれが発生してもカメラの向きが変わる事に気付きました。天板とマウスの本体の間は長いロッド(25cm位)が4本あるだけです。天板の締め付け力だけではねじれを防ぐのは難しいと感じましたが、対策方法はあるでしょうか? 
```

このような質問を投げかけて、AIからの回答をもとに対策を打っていきました。結果として、天板のネジが緩むことはなくなり、カメラの位置がずれることもなくなりました。

### ソフトウェアの開発は完全にお任せだったのか?

ちょくちょく間違った判断をするので以下のような感じで、疑問を投げかけて確認させる必要がありました。

```
❯ 「Pi の I2C はクロックストレッチが苦手」はRaspberry Pi 5でも該当しますか?     
```

このように、勘違いを指摘すると以下のように訂正してきますので、AIの判断が本当に正しいのかどうかを見定めるスキルは必要でした。

```
● 良い質問です。結論: あの有名なクロックストレッチ問題は Pi 5には基本的に該当しません。
  先の私の案内（研究時の「Pi 5でも該当」）は不正確でした。訂正します。
```

コードのレビューについては、作業時間の大半がレビューになってしまっている事に気付いてからはレビューはせずに実機での動作確認のみをするだけになりました。この点は、個人での開発だからできることだと思います。

## 感想

ハードウェアが関係するような開発でも、ソフトウェアの開発はAIに任せることができることが分かりました。ハードウェアの設計や製作についても、AIに任せることができる部分は多いと思います。来年の今頃には、CAD(Computer Aided Design)の分野でもAIがほぼ全ての設計を行い、人間はAIの判断が正しいかどうかを確認するだけの時代になっているのではないかと思いました。

結局、コンピュータを使った設計に関しては、人間は何をするかを決めてAIの設計が正しいのかを判断するだけになりそうです。
